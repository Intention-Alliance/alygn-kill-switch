## Browser Automation Insights & Solutions (2026-02-08 Final)

### CRITICAL BREAKTHROUGH: Sequential Action Problem (17:12 CST)

**Andler's insight:** "Why don't you try one by one instead of multiple at the same time?"

**This is the key:** Browser service can handle sequential individual actions with proper recovery time, but NOT rapid-fire multiple actions in succession.

**What we discovered:**

- ✅ Single action works perfectly (navigate, snapshot, click)
- ✅ Long timeouts (120s) work individually
- ❌ Multiple sequential actions cause: "ref is required" + port 18801 conflicts
- The issue: Browser service connection flakes on rapid sequencing, not on timeout duration

**Proven Pattern:**

```
Action 1: Navigate (120s) → ✅ OK
[Long wait]
Action 2: Snapshot (60s) → ✅ OK
[Long wait]
Action 3: Click (90s) → ✅ OK
[Long wait - CRITICAL]
Action 4: Type (90s) → ❌ FAILS (connection lost)
```

The service needs substantial recovery time between actions, not just timeout length.

### Browser Service Architecture Issue

**Root cause identified:**

- Browser service (port 18801) manages Chrome/Chromium sessions
- Single action = allocate resource, execute, release cleanly
- Sequential actions = gateway tries to reuse connection → gets stale
- "ref is required" error = browser lost context between calls

**Solution paths:**

1. **Add sleep() between actions** (60-120s minimum)
2. **One-at-a-time architecture** - publish 1 post, wait 2 min, publish next
3. **Chrome DevTools Protocol (CDP)** - keeps session alive, no reconnects
4. **X API write access** - eliminates browser layer entirely
